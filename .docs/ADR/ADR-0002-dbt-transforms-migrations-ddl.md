# ADR-0002 — dbt runs the transformations; migrations own DDL

- **Status:** Accepted (USER, 2026-09-25)
- **Resolves:** spec §0 "plain SQL or dbt-core for transforms"
- **Related:** ADR-0003 (schema `qbo`, roles, migrations), ADR-0008 (shared project)

## Context

The spec allows plain SQL or dbt-core for the raw → stg → mart transforms.
The USER decided: dbt for all transformations, except schema changes (DDL / init code).

## Decision

- **dbt-core with the dbt-postgres adapter** runs every transformation: raw → `stg_*` → `dim_*` / `fact_*` → serve views `vw_*`.
- **Migrations own DDL / init code** (ADR-0003): the schema, roles, grants, functions, and every table of spec §2 (`raw_entity`, `dim_*`, `fact_*`, `sync_state`, `qa_reports_snapshot`).
- dbt creates **views only** (`stg_*`, `vw_*`). It fills the migration-owned `dim_*` / `fact_*` tables through incremental models, and never creates, alters or drops a table:
  - every mart model: `materialized: incremental`, `full_refresh: false`, `on_schema_change: append_new_columns`. dbt then inserts only the model's columns, so the spec §2 identity keys stay generated by the database.
  - `dim_*`: `incremental_strategy: merge`, `unique_key: qbo_id`. `dim_account` leaves `stmt_section` / `stmt_group` / `stmt_sort` out of `merge_update_columns`, so consultant edits survive; the spec §3.3 defaults apply on insert only.
  - `fact_gl`: `incremental_strategy: delete+insert`, `unique_key: [txn_type, txn_qbo_id]`. A re-synced transaction replaces all its lines.
- dbt connects as `qbo_etl`. That role has DML rights on the tables but does not own them, so any DDL that dbt attempts on them fails on privileges.
- The dbt project lives in `dbt/` (project name `qbo_pnl`). Connection settings come from env vars via `env_var()` in `profiles.yml`; no password in the repo. dbt runs in the same Python 3.12 venv as the ETL; split the venvs only if pins conflict.

## Consequences

- Spec §2 DDL stays exact (identity keys, foreign keys, unique constraints), because dbt does not create the tables.
- Spec §3.1 "one unit test per DetailType" becomes dbt tests fed by `fixtures/`. The mechanism (dbt unit tests, or pytest loading fixtures into a disposable DB and then running `dbt build`) is settled in Phase 2. CI gains a `dbt build` step on the disposable DB.
- Gate P2 ("re-running transforms twice yields identical row counts") = `dbt build` run twice. A full reprocess uses a var (e.g. `--vars '{full_reload: true}'`), because `--full-refresh` is disabled for migration-owned tables.
- New dependency: `dbt-core` + `dbt-postgres`, pinned at install.
- The `dbt-fabric-warehouse` skill does not apply (it targets Fabric). SQL in dbt models follows `dax-sql-formatter`.
